# 逻辑分析指南（logic 维度）— code-check

## 定位

逻辑维度回答**"代码内部做得对不对"**——不依赖需求背景，对变更代码做静态逻辑分析，发现
控制流、数据流、状态机、边界条件、错误处理、并发、业务规则七类缺陷。

---

## 分析模型（三层）

```
第一层：变更识别（What Changed）
  变更位置 → 变更类型分类（控制流/数据流/状态转换/函数签名/错误处理）→ 影响范围（直接/间接/边界）
第二层：逻辑分析（Logic Analysis）
  控制流 / 数据流 / 状态机 / 边界条件 / 错误处理 / 并发控制 / 业务规则
第三层：影响评估（Impact Assessment）
  影响面 → 风险等级 → 修复建议
```

**影响范围识别**：直接影响 = 被修改函数及其调用者、被修改成员及其访问者；
间接影响 = 依赖返回值的代码、依赖状态的条件分支、调用链上层；边界 = 接口兼容/性能/资源/并发。

---

## 七大分析维度

### 1. 控制流

- [ ] **LOGIC-C01 死代码**：永假条件、return/break 后不可达语句
- [ ] **LOGIC-C02 逻辑矛盾**：互斥条件同真（`x > 10 && x < 5`）、重复条件、前置 return 后的重复判断
- [ ] **LOGIC-C03 条件覆盖不完整**：枚举分支遗漏、switch 缺 default、if-else 链遗漏状态

```cpp
// ❌ 典型：switch 缺 default，新枚举值静默漏过
switch (slotType) {
    case SOCIAL: HandleSocial(); break;
    case SERVICE: HandleService(); break;
    // 新增的 LIVE_VIEW 枚举无分支 → 静默不处理
}
```

### 2. 数据流

- [ ] **LOGIC-D01 未初始化**：条件分支下变量未在所有路径初始化即使用；成员变量未初始化（与 SEC-C01 重叠时合并）
- [ ] **LOGIC-D02 数据污染**：外部数据（IPC/分布式/文件）未校验直接进入敏感操作（与 SEC-F01 重叠时归安全维度，此处查传播路径）
- [ ] **LOGIC-D03 类型不匹配**：有符号/无符号比较（`int count < vector.size()`）；枚举强转越界；隐式窄化

### 3. 状态机（ANS 状态重点）

- [ ] **LOGIC-S01 非法转换**：状态转换未校验当前状态（如勿扰模式切换：类型变更时旧配置清理）
- [ ] **LOGIC-S02 状态不一致**：多个表示同一状态的变量未同步更新（单状态源原则）
- [ ] **LOGIC-S03 卡死状态**：无超时/恢复机制的等待状态（分布式同步等待对端应答、订阅会话建立）

**ANS 状态机检查点**：
- 订阅生命周期：注册 → 生效 → 退订，退订后回调不得再触发；订阅者死亡通知（进程退出）路径
- 发布流程：`advanced_notification_publish/` 各阶段状态推进与失败回退
- 勿扰模式：模式/类型/时间段三种配置的组合状态一致性

### 4. 边界条件

- [ ] **LOGIC-B01 越界**：循环边界 `<=` vs `<`；容器索引未校验；memcpy 长度未校验目标容量
- [ ] **LOGIC-B02 空指针**：解引用前未判空；判空后又解引用（判空作用域外使用）；返回值指针未校验（`readParcelable` 结果直接使用）
- [ ] **LOGIC-B03 整数溢出**：数量累加无上限（通知计数器）、乘法求 size、`int` 索引回绕（与 SEC-E04/E05 重叠时归安全维度）

### 5. 错误处理

- [ ] **LOGIC-E01 遗漏错误路径**：可失败调用（IPC、DB、文件）返回值未检查即继续
- [ ] **LOGIC-E02 部分失败不一致**：多步操作中途失败，前序副作用未回滚（内存已改、DB 未写——ANS 偏好设置高发）
- [ ] **LOGIC-E03 错误吞没**：捕获/检查了错误但只打日志继续执行，错误码未向上传递
- [ ] **LOGIC-E04 资源泄漏**：错误路径资源未释放（锁、内存、文件句柄、事件订阅）

```cpp
// ❌ 典型：错误路径锁未释放（ScopeGuard 缺失）
mutex_.lock();
ret = SaveToDb();          // 失败
if (ret != ERR_OK) {
    return ret;            // ❌ mutex_ 永远不释放
}
mutex_.unlock();
// ✅ 使用 std::lock_guard / ffrt 作用域锁等 RAII 锁
```

### 6. 并发控制

- [ ] **LOGIC-N01 死锁**：锁顺序不一致；持锁回调（锁内触发订阅者 IPC 回调，回调再取同一锁）
- [ ] **LOGIC-N02 竞态（Check-Then-Act）**：先检查后使用之间状态可被并发修改（先查订阅者存在再回调，中间被退订 → 回调悬空）
- [ ] **LOGIC-N03 数据竞争**：共享容器（通知列表/订阅者表）读写未全部持锁；`std::atomic` 使用正确性

```cpp
// ❌ 典型：Check-Then-Act 竞态（subscriber_manager 高发模式）
if (subscribers_.find(id) != subscribers_.end()) {     // 检查
    subscribers_[id]->OnNotify(notification);          // 使用：中间可能被退订线程删除 → 悬空
}
// ✅ 检查与使用在同一临界区内，且回调在锁外执行（拷贝后释放锁再回调）
```

### 7. 业务规则与不变性

- [ ] **LOGIC-R01 不变性破坏**：通知数量上限、订阅者数量上限在所有写入路径维护（新增路径漏检）
- [ ] **LOGIC-R02 契约违反**：函数前置条件未验证（除数非零、容器非空）；后置条件不保证（返回值唯一性）
- [ ] **LOGIC-R03 计数/一致性**：通知计数（角标数据源）增减在异常路径保持配对

## 检查清单汇总（按变更类型选用）

| 变更类型 | 重点维度 |
|---|---|
| 新增 if/switch 分支 | C03（覆盖完整）、D01（分支初始化） |
| 修改条件/默认值 | C02、D03（类型匹配） |
| 新增/修改状态字段 | S01~S03、N02~N03 |
| 修改锁使用 | N01~N03、E04 |
| 新增 IPC 处理函数 | B02、E01、N02（回调时序） |
| 修改容器操作 | B01、N03、R01 |

## 检测方法

1. `git diff` 逐 hunk 分类变更类型（模型第一层）
2. 追踪被改函数的调用者与被调用者（影响范围）
3. 对每个 hunk 应用对应重点维度检查清单
4. 竞态/死锁类发现须画出线程路径（发现点 → 持锁点 → 回调点）

## 严重等级映射

| 类别 | 默认等级 |
|---|---|
| 死锁、UAF/悬空回调、状态卡死、错误路径数据不一致 | **P0** |
| Check-Then-Act 竞态、条件覆盖缺失、未检查错误继续执行、资源泄漏 | **P1** |
| 死代码、冗余条件、类型不匹配警告、弱不变性 | **P2** |
| 风格性逻辑简化建议 | **P3** |
