# Refuter 质疑规则与判定标准 — code-check

> 本文件是 SKILL.md Step 5（Refute — 对抗性验证）的详细规则。
> 原则：**只质疑，不发现**——refuter 不能新增任何维度检视未报告的发现。质疑必须有代码证据。
> 目的：过滤误报与夸大，确保门禁报告的每条发现都经得起推敲。

---

## 1. 审查范围

| 优先级 | 审查策略 |
|--------|---------|
| P0（致命） | **全量审查**。推翻需要"确认不可达"级别的证据，不允许仅凭"极难触发"推翻 |
| P1（严重） | **全量审查**。推翻需要"上游有可靠防护"级别的证据 |
| P2（一般） | **抽样审查**（30% 或至少 5 条），优先审"可触发性存疑"的发现 |
| P3（提示） | 不进入 refute，直接进入最终报告的"建议跟进" |

**推翻 vs 降级**：
- 推翻 = 该发现从最终报告中移除（仍保留在 refute_log.md 中，便于人工复核捞回）
- 降级 = 该发现保留在报告中，严重等级下调（如 P0→P1、P1→P2）

## 2. 三层质疑

### 2.1 第一层：触发路径证伪 —— "真的能被触发吗？"

对每个发现，从发现点往上追溯调用链。

| 质疑点 | 检查方法 | 推翻/降级标准 |
|--------|---------|--------------|
| 上游空指针防护 | 追溯发现点函数的调用者，检查传入参数前是否有 `if (ptr == nullptr) return` | 上游有可靠防护 → 推翻 |
| 不可达路径 | 检查发现点是否在 `#ifdef DEBUG`、特性开关关闭分支、已废弃函数、仅测试代码路径 | 确认不可达 → 推翻 |
| 数据来源为常量 | 标注为"外部输入"的变量，上游是否为 `static const` 或编译期已知值 | 确认常量 → 推翻 |
| IPC 接口暴露面 | 检查 IPC 入口的调用方权限：`AnsManagerStub` 的该接口是否仅系统应用/系统进程可调（`AccessTokenHelper` 校验）、是否有权限拦截 | 仅系统进程可调 + 调用方可信 → 降一级 |
| 断言/解析防护 | 上游有 `assert(ptr != nullptr)` 或解析层自带边界校验 | assert 不可靠（release 不生效）→ 维持；解析层可靠 → 推翻 |
| 特性开关防护 | 发现点位于 `notification.gni` 某特性开关（如 `distributed_notification_service_feature_*`）的条件编译内 | 开关默认关闭且产品不启用 → 降一级（不得推翻：开关可被产品打开） |
| 弱防护 | 上游有检查但不完整（如仅检查 nullptr 但没检查空字符串、仅检查长度上限但没检查下限） | 降一级 |

### 2.2 第二层：影响夸大证伪 —— "后果真的这么严重吗？"

| 误报模式 | 常见案例 | 复审方法 | 判定 |
|---------|---------|---------|------|
| Defensive double-free | `free(ptr); ptr = nullptr;` 再 free | 检查两次 free 之间 ptr 是否被置 null | 有置 null → **推翻** |
| 进程退出时资源泄漏 | 静态分配的资源在进程退出时未释放 | 检查泄漏点是否在 exit() 路径上 | OS 自动回收 → **降级为 P3** |
| 整数溢出不可达 | 标注 `int a = b + c` 溢出，但 b 和 c 均来自 `uint8_t` | 计算实际输入范围 | 不可溢出 → **推翻** |
| UAF 仅涉及日志打印 | "释放后使用"仅在 `ANS_LOGI` 中读整数值 | 检查 use 点是否影响控制流或数据完整性 | 仅日志 → **降两级** |
| 回调泄漏但数量有限 | 标注"回调未清理导致泄漏"，但订阅者/回调总数有上限 | 计算实际泄漏上限 | 上限小 → **降级** |
| 静态 bool 标志位无锁 | 标志位用于一次性初始化 | 检查是否只在单线程初始化阶段设置 | 单次设置 → **降级为 P3** |
| 通知内容泄漏仅在 DEBUG 日志 | 标注"敏感信息打印"，但日志级别为 DEBUG（正式版本默认不打印） | 确认日志宏级别与发布版本行为 | 仅 DEBUG → **降一级**（不得推翻：调试版本仍会打印） |
| 偏好设置读取失败有降级路径 | 标注"配置读取失败导致功能异常"，但代码有默认值兜底 | 检查失败分支是否返回默认配置 | 有兜底 → **降级** |

### 2.3 第三层：跨维度根因去重 —— "这两个发现本质是同一个根因吗？"

不同于 `file:line` 机械去重，基于修复方案反推。

**判定流程**：

1. **同一修复改动**：如果两个发现的修复方案是同一处改代码 → 合并
   - 例：SEC-005（空指针）+ LOGIC-004（状态更新异常）+ SEC-007（异常路径未释放锁）→ 根因是 `services/ans/src/notification_subscriber_manager.cpp:412` 缺一次 nullptr 检查，合并为一条
2. **连锁影响**：如果发现 B 是发现 A 的直接后果 → 合并到根因
   - 例：缺少边界校验 → 导致越界写入 → 导致相邻内存损坏 → 合并为一条"缺少边界校验"
3. **独立发现**：即使出现在同一文件，如果修复需要改动不同代码位置 → 维持独立
   - 例：同一文件的锁顺序问题和资源泄漏问题 → 维持两条

## 4. refute 的约束

- **只质疑，不发现**：refuter 不能新增任何维度检视未报告的发现
- **质疑必须有代码证据**：推翻或降级必须引用具体 `file:line`
- **被推翻的发现保留在 refute_log.md**：不进入统一报告正文，在 refute_log.md 中列出条目和理由，便于人工复核捞回
- **P0 推翻需更严格证据**：不能仅凭"极难触发"推翻 P0，必须是"确认不可达"（上游硬 guard 或编译器保证）；IPC 接口"仅系统应用可调"不足以推翻 P0——系统应用也可能被攻破或存在提权路径，只能降级
- **refute_log.md 与最终报告一并交付**：两者缺一不可
